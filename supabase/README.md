# Coach HQ database (Supabase / PostgreSQL)

| File | What it does |
|---|---|
| `migrations/20261101000000_schema.sql` | Tables, types and indexes for the whole platform |
| `migrations/20261101000100_security.sql` | Row Level Security (who can read/write what) and the functions the apps call |
| `migrations/20261101000200_storage.sql` | Private `inbody` storage bucket for uploaded reports |
| `migrations/20261113000000_public_pages.sql` | Coach public pages (`/c/<handle>`) and the join requests they produce |
| `migrations/20261113000100_trainee_app.sql` | Daily habits, cardio, skipped sessions -- what the Flutter app logs |
| `seed.sql` | `load_demo_data(coach_id)`: fills one coach account with the demo workspace (generated, see below) |
| `tests/` | Runs the migrations on a plain local PostgreSQL and checks the access rules (no Docker needed) |

## Data model

- Every record belongs to a **coach**, directly (`templates`, `calls`, `import_layouts`) or through a **trainee**.
  The platform is ready for many coaches; each sees only their own trainees.
- `trainees.user_id` links a trainee profile to the trainee's own login once they sign in to the app.
- Training days live as JSON inside `templates.days` and `program_weeks.days` (always edited one week at a time).
  Workout logs are fully relational (`workout_logs` → `log_entries` → `log_sets`) for PRs and analytics.
- Money is SAR (`memberships.price_sar`). Coach-only fields (the pinned note) live in `trainee_private`.
- `coach_pages` is the coach's public page, kept apart from `coaches` because RLS grants rows, not
  columns: the page is world-readable, while the coach's email and dashboard preferences are not.
- `join_requests` is what the public page produces. The intake answers live in one `answers` JSON
  blob, since the form on the site owns its own shape.
- `daily_logs`, `cardio_sessions` and `skipped_sessions` are what the trainee app logs beyond
  workouts. Their ids are generated by the client, so a change resent from the app's offline
  outbox collides with the primary key instead of being logged twice.

## Access rules (enforced by the database)

- **Coach:** everything for their own trainees; nothing from other coaches.
- **Trainee:** reads their own profile, goals, membership, program, calls and *shared* notes; adds their own
  workouts, weigh-ins, check-ins, InBody scans, metric values and messages. Never sees private notes,
  the pinned note, templates or the coach's focus blocks; cannot change their plan or send as the coach.
- **Not signed in:** nothing, except a coach page whose `published` is true.
- **A visitor:** sends one pending join request at a time, as themselves, to a coach whose page is
  published, and reads their own afterwards. They cannot change it, approve it, or see anyone else's.

## Set up a Supabase project

1. Create a project at supabase.com (choose the region; see the data-residency note below).
2. Apply the migrations, either:
   - **CLI:** `npx supabase login`, `npx supabase link --project-ref <ref>`, `npx supabase db push`; or
   - **Dashboard:** paste each file in `migrations/` into the SQL editor, in order.
3. Paste `seed.sql` into the SQL editor once (it only defines the demo function).
4. Authentication → enable **Confirm email** (trainee profiles are claimed by verified email).
5. Project Settings → API: copy the **Project URL** and **anon / publishable key** into `web/.env.local`:
   ```
   VITE_SUPABASE_URL=https://<ref>.supabase.co
   VITE_SUPABASE_ANON_KEY=<anon key>
   ```
6. Sign up as a coach (user metadata `{"role": "coach"}` creates the coach profile), then load the demo:
   `select public.load_demo_data('<your user id>');`

Never put the service-role key in the web app.

**Data residency:** trainee body data, injuries and InBody results are health data under Saudi PDPL.
If it must stay in Saudi Arabia, self-host Supabase (open source) on a Saudi cloud region; the same
migrations apply unchanged.

## Test the app against it, end to end

The checks above run in SQL. To exercise the app's own data layer -- `src/data/remote.ts`, the
real `@supabase/supabase-js` client, the PostgREST wire format and Row Level Security together --
serve the scratch database over HTTP and point the harness at it:

```bash
brew install postgrest
# postgrest.conf: db-uri, db-schemas = "public", db-anon-role = "anon", jwt-secret = <32+ chars>
postgrest postgrest.conf          # serves the schema on :3000, exactly as Supabase does
```

`supabase-js` calls `<url>/rest/v1/...`, so put a small proxy in front that strips the prefix,
then mint an HS256 token with `sub` set to a coach's user id and `role` set to `authenticated`:

```bash
cd web && npx tsx scripts/e2e-remote.ts http://127.0.0.1:3001 "$COACH_JWT" "$COACH_ID" "$TRAINEE_JWT" "$TRAINEE_ID"
```

It loads a whole workspace, writes changes back (including the trainee app's habits, cardio and
skips), reloads to confirm they stuck, and then loads the same database as the trainee to check
she sees only her own data. The same API also runs the web app itself: set `VITE_SUPABASE_URL` to
the proxy and the dashboard works against real PostgreSQL rather than demo data.

`tests/local-shim.sql` imitates the bits of Supabase the migrations use (`auth.users`, `auth.uid()`,
the `anon`/`authenticated` roles, a storage stub). Never run it against a real Supabase project.

## The public page and the join flow

A coach claims a handle and publishes their page:

```sql
insert into coach_pages (coach_id, handle, published, whatsapp)
values ('<coach user id>', 'omar', true, '966500000000');
```

The page then lives at `/c/omar` and anyone can read that row. A visitor who signs up and sends the
intake form gets a row in `join_requests` with `status = 'pending'`, which shows up in the coach's
dashboard under **Requests**. From there the coach either:

- **approves it** -- `select public.approve_join_request(<request id>, 'premium', 'Premium online coaching', 899, 'monthly');`
  creates the trainee in `onboarding`, links their auth account, carries the intake answers across
  (name, birth date, height, goal, training days, injuries) and files the membership. The plan name
  and price come from the caller so `web/src/data/plans.ts` stays the only price list;
- **declines it** -- `select public.decline_join_request(<request id>);`
- **or messages them on WhatsApp first**, from the phone number on the request.

The dashboard does all of this through `web/src/data/joinRequests.ts`, which is also what the public
site's pages call instead of their mocked `site/services/joinRequests.ts` and `site/services/coachProfiles.ts`.

## What the trainee app calls

The Flutter app in `../mobile` talks to this database directly (`supabase_flutter`), with no
server of its own. Row Level Security is the only thing deciding what it may touch, so the app
holds no access rules and the coach dashboard and the phone enforce exactly the same ones.
`supabase/tests/rls-check.sql` checks every line of this table.

**Signing in.** `auth.signInWithPassword`, then `select public.claim_trainee_profile();` once.
That links the auth account to the profile the coach created with the same (verified) email and
returns its id. A trainee whose email isn't confirmed gets null and sees nothing.

**Reading.** Each screen selects the tables it needs; RLS narrows every one of them to the
signed-in trainee. There is no snapshot endpoint to keep in step any more:

| Screen | Tables |
| --- | --- |
| Today, Train | `trainees`, `programs`, `program_weeks`, `workout_logs`, `skipped_sessions`, `calls` |
| Workout | `workout_logs` → `log_entries` → `log_sets` |
| Progress | `workout_logs`, `weights`, `checkins`, `inbody_scans`, `cardio_sessions`, `metric_entries` |
| Habits, Body | `daily_logs`, `cardio_sessions`, `weights`, `inbody_scans`, `inbody_requests` |
| Coach | `messages`, `notes` (shared only), `coaches`, `calls` |
| Me | `trainees`, `goals`, `memberships` |

Two things the old `/api/app/me` returned are now unreachable by design: the coach's pinned note
(`trainee_private`, coach-only) and private notes. `snapshotFor()` sent the whole trainee record,
pinned note included; going direct makes that leak impossible rather than a thing to remember.

**Writing.** Every op in the old `web/server/appOps.ts` becomes one call. The app keeps its
offline outbox; what changes is that each queued change carries the row's uuid, so resending
after a dropped connection collides with the primary key instead of needing a list of applied
op ids:

| Old op | Now |
| --- | --- |
| `log` | insert `workout_logs`, then its `log_entries` and `log_sets` |
| `weight` | upsert `weights` on `(trainee_id, date)` |
| `checkin` | upsert `checkins` on `(trainee_id, date)`, and the weigh-in it carries into `weights` |
| `message` | insert `messages` with `sender = 'trainee'` |
| `seen` | `select public.mark_coach_messages_seen(<trainee id>);` |
| `touch` | `select public.touch_last_seen();` |
| `inbody` | upload the photo to the private `inbody` bucket under `<trainee id>/`, then insert `inbody_scans` with its `file_path`. A trigger closes the coach's pending request |
| `daily` | upsert `daily_logs` on `(trainee_id, date)` |
| `cardio` | insert `cardio_sessions` |
| `skip` | upsert `skipped_sessions` on `(trainee_id, week_start, day_id)` |
| `unskip` | delete the `skipped_sessions` row by id |

The app never sends a trainee id it chose: RLS derives it from the token, and a write naming
anyone else is rejected by the database. Validation that used to live in `isValidOp()` is now
check constraints on the columns, so the dashboard, the phone and any future client get it.

**Live updates.** Supabase Realtime on the tables above replaces the `/api/events` stream the
local sync API used.
